<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| crates.io → developer machine | `cargo install cargo-dist --locked` downloads a binary from crates.io that will, in Plan 03, run our release pipeline. Compromise here would compromise every future release. Mitigated by `--locked` + version pin to 0.32.0 + RESEARCH § Package Legitimacy Audit (Stack-locked since Phase 0). |
| `cargo dist init` → Cargo.toml + .github/workflows/release.yml | cargo-dist writes a 200+ line YAML and a TOML block; it executes in our environment with our cargo identity. Risk: malicious version of cargo-dist could add a malicious step to release.yml (run on every future tag push). Mitigated: version pin + Task 1 acceptance asserts release.yml structure matches expected jobs (plan/build-local/build-global/host/publish-homebrew). |
| local manifest → future CI runner | The `[workspace.metadata.dist]` block is read by the GH Actions runner on every tag push (Wave 3). A typo here means a malformed release. All assertions land in Task 1 acceptance gates. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-SC | Tampering / Supply-chain | `cargo install cargo-dist --version 0.32.0 --locked` | mitigate | Locked version pin + `--locked` flag + Package Legitimacy Audit (already passed in RESEARCH — 0.32.0 stable, axodotdev signed, 3+ year crate age). cargo-dist is dev-tool only, NOT added to `Cargo.toml [dependencies]`, so the supply chain risk is limited to release-time pipeline (not runtime ahb users). |
| T-04-06 | Tampering | `.github/workflows/release.yml` generated by cargo-dist | mitigate | Task 1 acceptance asserts presence of expected jobs (plan/build-local/build-global/host/publish-homebrew) and the `HOMEBREW_TAP_TOKEN` reference; an attacker swapping in a different cargo-dist version would have to silently match this exact job topology or the gate fails. |
| T-04-07 | Information disclosure | `cargo dist plan` output | accept | Output is benign metadata (target list, installer list, formula name); committed into `.planning/phases/04-.../04-02-DRY-RUN.md` which is excluded from the crate tarball (D-82) but stays in the public GitHub repo — that's the desired evidence trail visibility. |
| T-04-08 | Denial of service | `[profile.release].lto = true` build time | accept | Full LTO doubles release build time on the dev box; we have one dev, one box, no CI cost (CI uses thin-LTO via `[profile.dist]`). Acceptable trade for cold-path perf + smaller binary. |
| T-04-09 | Tampering | `formula = "ahb"` manual patch | mitigate | The manual patch is a single literal line under `[workspace.metadata.dist]`; Task 1 grep gate asserts its presence. Without this patch the homebrew formula would silently inherit the crate name `ai-hp-bar` and break the D-78/D-79 user contract `brew install True347/tap/ahb` — a UX bug, not a security one, but caught by the grep. |
</threat_model>
